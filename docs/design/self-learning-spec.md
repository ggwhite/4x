# Self-Learning Framework — Spec

> 讓每個使用 4x 的專案自動累積、注入、驗證操作知識。

## 問題

LLM session 的操作經驗（環境 troubleshoot、build workaround、帳號問題）隨 session 結束消失。後續 session 重複踩同樣的坑。現有 learnings.json 只捕獲設計/品質教訓，操作知識完全缺失；且知識只在 4x role 內流通，standalone session 讀不到也寫不回。

## 設計原則

- 知識沉澱的單位是**專案**，不是工具、session、角色
- learnings.json 是唯一的知識庫，不另建平行系統
- 新知識要有品質閘門（candidate），不是每條都直接進 prompt
- 讀寫不綁定 4x role——standalone session 也能參與

## Feature 拆分

```
F1: ops-category ──┬── F2: learn-add-cli
                   ├── F3: candidate-status ── F5: learning-effectiveness
                   └── F4: learn-context
```

F1 是基礎；F2/F3/F4 互相獨立可平行；F5 依賴 F3。

## F2: learn-add-cli

### 目標

讓 standalone session 可以透過 CLI 寫入 learning，不需要走 4x role pipeline。

### 新增 subcommand

```
4x learn add --category <cat> --content <text> [--json]
```

### 行為

- 先呼叫 `Store.FindSimilar(content) *Entry` 檢查是否已有相似條目
  - 若命中 → 報 `"similar learning already exists: Lxxx"`，不寫入
  - 若未命中 → 呼叫 `Store.Harvest()` 寫入
- `sourceFeature = "manual"`，`sourceRole = "user"`
- status 依 F3 的 candidate 機制（F3 未完成前先 active）

### 新增方法

`Store.FindSimilar(content string) *Entry`：三層比對（exact → normalized → Jaccard），回傳第一個命中的 Entry，未命中回傳 nil。抽取自 `Harvest()` 內部的去重邏輯，兩者共用。

### 驗證

| 條件 | 結果 |
|------|------|
| category 不在白名單 | 報錯，列出合法值 |
| content 為空 | 報錯 |
| content 與既有 fuzzy 重複 | 報 similar exists，不寫入 |
| 正常寫入 | 印出新 ID，exit 0 |

### 檔案

`cmd/4x/learn.go` 新增 `newLearnAddCmd()`，加到 `newLearnCmd()` 的 `AddCommand`。

### 測試

- `TestLearnAdd_Success`：正常寫入，verify store 多一條
- `TestLearnAdd_InvalidCategory`：報錯
- `TestLearnAdd_FuzzyDuplicate`：不寫入
- `TestLearnAdd_JSON`：JSON 輸出格式正確

## F3: candidate-status

### 目標

新 harvest 的 learning 不直接注入 prompt，需要跨 feature 驗證後才升級為 active。

### Status 生命週期

```
candidate → active → stale → (pruned)
                  → promoted
```

新增 `StatusCandidate Status = "candidate"`。

### Harvest 行為變更

所有 harvest 進來的 learning 預設 `status: candidate`。

Fuzzy match 命中時的行為改為三種情況：

| match 對象 | 行為 |
|-----------|------|
| active entry | skip（去重，同現在） |
| 同 feature 的 candidate | skip（去重） |
| **不同 feature** 的 candidate | 升級那條 candidate 為 active，新的不寫入 |

### Designer select 升級

`LoadActiveLearnings()` 擴充為回傳 active + candidate（candidate 標註 `[candidate]`）。

Designer 的 `selected-learnings.json` 若選了 candidate → `UpdateLearningsUsage()` 時升級為 active。

### CLI 調整

`4x learn list`：
- 預設列出 active + candidate
- candidate 條目加 `*` 標記
- `--status <status>` flag 可過濾

### 向後相容

既有 active learning 保持 active，只有新 harvest 的才是 candidate。

### 改動檔案

| 檔案 | 改動 |
|------|------|
| `internal/learning/store.go` | `StatusCandidate`、`Harvest()` 邏輯（candidate 預設 + 跨 feature 升級） |
| `internal/prompt/learnings.go` | `LoadActiveLearnings()` 含 candidate、`UpdateLearningsUsage()` 升級 |
| `templates/designer.md.tmpl` | candidate 標註 |
| `cmd/4x/learn.go` | list `--status` flag |

### 測試

- `TestHarvest_NewEntryIsCandidate`：新 harvest 的是 candidate
- `TestHarvest_CrossFeatureFuzzyPromotes`：不同 feature 的 fuzzy match 觸發升級
- `TestHarvest_SameFeatureFuzzySkips`：同 feature 不升級
- `TestUpdateUsage_PromotesCandidate`：Designer select 觸發升級
- `TestLearnList_StatusFilter`：`--status` 過濾

## F4: learn-context

### 目標

產生 learnings 的 markdown snapshot，讓 standalone session 透過 CLAUDE.md `@` include 讀到。

### 新增 subcommand

```
4x learn context [--json]
```

### 產出

寫入 `.4x/learnings-context.md`：

```markdown
<!-- Auto-generated by 4x learn context. Do not edit manually. -->
# Learnings

## design
- 復用既有結構...

## ops
- 在 worktree 內跑 go build 前必須設 GOWORK=off...
```

只含 active 條目，按 category 分組。

### 自動刷新

兩個時機自動呼叫 context 產生：
1. `HarvestLearnings()` 寫入成功後
2. `ApplyConsolidateResult()` 成功後

`internal/prompt/learnings.go` 新增 `GenerateLearningsContext(ws)` 函數，上述兩處呼叫。

### Git 處理

`learnings-context.md` **不加** `.4x/.gitignore`——應被 commit，clone 下來也能讀到。

### CLAUDE.md 整合

`4x init` 產生的 CLAUDE.md template 加入：

```
@.4x/learnings-context.md
```

既有專案需手動加（或 `4x learn context` 執行後提示 user）。

### 檔案

| 檔案 | 改動 |
|------|------|
| `internal/prompt/learnings.go` | 新增 `GenerateLearningsContext()` |
| `internal/prompt/learnings.go` | `HarvestLearnings()`、`ApplyConsolidateResult()` 呼叫 |
| `cmd/4x/learn.go` | 新增 `newLearnContextCmd()` |
| `cmd/4x/init.go` | CLAUDE.md template 加 `@` |

### 測試

- `TestGenerateLearningsContext_GroupsByCategory`：按 category 分組
- `TestGenerateLearningsContext_OnlyActive`：不含 candidate/stale/promoted
- `TestLearnContext_CLI`：CLI 寫入檔案

## F5: learning-effectiveness

> **狀態更新（F187, 2026-08）**：本節描述的 `MarkIneffective()` 已改名為 `ReevaluateIneffective()`，判定條件 3 由「最近 3 個不同 feature 的 entries 中有同 category」改為「相似內容（Jaccard ≥ `RecurrenceSimilarityThreshold`）來自 ≥ `RecurrenceMinDistinctFeatures` 個相異 feature」，且旗標可雙向重評（條件不再成立即撤銷）。以下內容為 F119 當時的設計紀錄，實作以 `internal/learning/store.go` 為準。

### 目標

追蹤 learning 注入後是否減少同類問題，標記無效 learning 供 review。

### Entry 新增欄位

```go
ActivatedAt time.Time `json:"activated_at,omitempty"`
```

F3 的升級邏輯設定此欄位。

### Proxy 指標

在 `HarvestLearnings()` 時掃描 active learning：

一條 active learning 被標記為 `ineffective` 的條件（全部滿足）：
1. `used_count >= 3`（已被注入多次）
2. `ActivatedAt` 距今 > 30 天（有足夠觀察期）
3. 最近 3 個 feature 仍產出同 category 的新 learning

**不自動刪除**，只標記。

### CLI

`4x learn list --ineffective`：只列出被標記的條目。

### 延後實作

此 feature 可延後。前四個做完已覆蓋完整的讀寫迴圈，F5 需要累積數據才有意義。

### 檔案

| 檔案 | 改動 |
|------|------|
| `internal/learning/store.go` | `ActivatedAt` 欄位、`MarkIneffective()` 方法 |
| `internal/prompt/learnings.go` | `HarvestLearnings()` 掃描 proxy |
| `cmd/4x/learn.go` | `--ineffective` flag |

### 測試

- `TestMarkIneffective_MeetsAllConditions`：三條件都滿足時標記
- `TestMarkIneffective_NotEnoughUsage`：used_count 不足不標記
- `TestMarkIneffective_TooRecent`：觀察期不足不標記
