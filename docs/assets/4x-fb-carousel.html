What is 4x?

把 AI 開發從「單人衝刺」變成「工程流程」。

4x 是一個多角色 AI 開發框架，把真實軟體工程拆成 Design、Code、Review、Test 四個階段，讓不同 AI agent 各司其職。

核心想法：不要讓同一個 AI 同時設計、實作、審查、測試。角色隔離可以降低自我審查偏見，讓複雜功能更可控。
Role isolation 設計、實作、審查、測試分開跑，避免同一段上下文互相污染。
CLI guardrail 範圍、狀態、證據由 Go CLI 強制，不靠 AI 自己乖。
File protocol 所有角色透過 .4x/ artifacts 協作，可以中斷續跑。
給大型功能、重構、跨模組變更的 AI 工作流 github.com/ggwhite/4x

Four roles

四個角色，各自負責一段工程判斷。

Design
01

先釐清需求、限制、風險與驗收標準。Designer 不寫程式，只負責把「要做什麼」講清楚。

Code
02

Coder 根據規格實作，不自己批准自己的產出。它只拿到該看的上下文，避免無限發散。

Review
03

Reviewer 用對抗視角檢查：範圍是否越界、設計是否被破壞、錯誤處理是否足夠。

Test
04

Tester 依照事前標準驗證，而不是照 Coder 的說法相信它。結果必須留下可檢查證據。

Why split the loop?

單一 agent 快，但容易把自己的錯誤合理化。

單一 agent

速度快，但一邊寫一邊審，容易自我說服。
設計、實作、審查混在同一段上下文，偏見會互相污染。
適合小修、小腳本、低風險改動。

4x loop

每個角色只做自己的工作，責任邊界清楚。
Reviewer 不替 Coder 圓場，Tester 不照 Coder 自述驗收。
適合大型 feature、重構、跨模組與高風險變更。
4x 不是追求最少步驟，而是把「會出錯的地方」拆開，讓每一步都有獨立檢查。

04/05
Guardrails

4x 的安全邊界不是 prompt，是工具強制。

狀態機 init → designing → coding → reviewing → testing → accepting，流程可追蹤，也能阻止亂跳階段。
檔案協定 所有角色透過 .4x/ 交換 artifact，不依賴共享腦內上下文，也不需要 CLI 直接呼叫 LLM。
可續跑 Session 中斷、機器重開、runner crash 後，4x run 可以從已保存的狀態與證據繼續。
AI 負責判斷，CLI 負責邊界。 .4x/ protocol

05/05
Fit

用速度和 token 成本，換結構與正確性。

適合

大型功能開發，需要明確 spec 與驗收。
跨模組重構，容易破壞既有行為。
需要 review / test 證據，不只看 AI 自述。

不適合

一行 bug fix、一次性腳本、低風險小改。
token 預算很緊，不能接受多輪 agent。
需求仍然模糊，還沒有可驗收標準。
