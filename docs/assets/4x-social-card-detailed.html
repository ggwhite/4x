Multi-Role AI
Development Loop
AI coding workflow

把 AI 開發從「單人衝刺」變成「工程流程」。

4x 是一個多角色 AI 開發框架，把真實軟體工程拆成 Design、Code、Review、Test 四個階段，讓不同 AI agent 各司其職。

核心想法：不要讓同一個 AI 同時設計、實作、審查、測試。角色隔離可以降低自我審查偏見，讓複雜功能更可控。
四個角色，各自負責一段工程判斷
Design
01

先釐清需求、限制、風險與驗收標準。Designer 不寫程式，只負責把「要做什麼」講清楚。

Code
02

Coder 根據規格實作，不自己批准自己的產出。它只拿到該看的上下文，避免無限發散。

Review
03

Reviewer 天生用對抗視角檢查：範圍是否越界、設計是否被破壞、錯誤處理是否足夠。

Test
04

Tester 依照事前標準驗證，而不是照 Coder 的說法相信它。測試結果必須留下可檢查證據。

跟單一 agent 最大的差別

單一 agent

速度快，但容易一邊寫一邊合理化自己的錯誤。
設計、實作、審查混在同一段上下文裡，偏見會互相污染。
適合小修、小腳本、低風險改動。

4x loop

每個角色只做自己的工作，責任邊界清楚。
CLI 用狀態機、scope lock、證據要求強制流程，不靠 AI 自律。
適合大型 feature、重構、跨模組與高風險變更。
4x 的 guardrail 不是 prompt，是工具強制
狀態機 init → designing → coding → reviewing → testing → accepting，流程可追蹤。
檔案協定 所有角色透過 .4x/ 交換 artifact，不依賴共享腦內上下文。
可續跑 Session 中斷或機器重開後，4x run 能從中斷點恢復。
什麼時候適合用？什麼時候不要用？

適合

大型功能開發，需要明確 spec 與驗收
跨模組重構，容易破壞既有行為
需要 review / test 證據，而不是只看 AI 自述

不適合

一行 bug fix、一次性腳本、低風險小改
token 預算非常緊，不能接受多輪 agent
需求本身很模糊，還沒有可驗收標準

brew install ggwhite/tap/fourx
